## 二、核出来的 bug（已修）

### 1. `S` 操作符语义错了（真 bug）

标准表36：

```
S  x y    定义子绘制图形边线的起始点坐标(x,y)
```

我原来照 SVG 把 `S` 当成 smooth-quadratic（4 个操作数），真实文件用 `S` 定义子路径起点时会整体错位。

已改：`"S": 2`，并走与 `M` 相同的分支（flush 当前子路径 + 起新子路径），但不像 `M` 那样把后续坐标按 `L` 处理。

验证：

```
S 10 10 L 50 10 L 50 40 C   ->  1 子路径 closed=True pts=3
```

### 2. `Fill` 默认值错了

标准表45：`Fill` **默认 true**，`Stroke` 默认 false。

我原来没写 `Fill` 就当作不填充，导致"有描边没写 Fill"的对象被跳过。数电发票的框线恰好写了 `Fill="false"` 才没暴露。

已改：没写 `Fill` 时返回 True（真实文件里想纯描边的都会显式写 `Fill="false"`）。

### 3. 页面 `Area` 的回退链不全

标准表12：

> `Area` 该节点不出现时则**使用模板页中的定义**，如果模板页不存在或模板页中没有定义页面区域，则**使用文件 CommonData 中的定义**

我原来直接从页面 Area 跳到 CommonData，跳过了模板页。

已改：页面 `Area` → 所引用模板页的 `Area` → `CommonData/PageArea`。

## 二·补：读正文又抓出来的四个错（已修）

上一轮只做了 XSD 结构校验，这轮逐条读正文表格，又找出四处实现与原文不符。

### 1. 图形对象与文字对象的默认值不是一套（表35 vs 表45）

我原来用同一组默认值，实际上两张表完全不同：

| 属性 | 表35 图形对象 | 表45 文字对象 |
|---|---|---|
| `Stroke` | 默认 **true** | 默认 **false** |
| `Fill` | 默认 **false** | 默认 **true** |
| `FillColor` | 默认**透明** | 默认**黑色** |
| `StrokeColor` | 默认黑色 | — |

后果：一个只画线、写了 `StrokeColor` 但没写 `Stroke`/`Fill` 的 `PathObject`，
用文字对象的默认值去判断会被当成"不描边不填充"直接跳过。反过来，一个没写
`FillColor` 的填色路径，会被画成黑色实心块。

已按类型分别设 `FILL_DEFAULT` / `STROKE_DEFAULT` / `FILL_COLOR_DEFAULT`。验证：

```
只写 StrokeColor       -> has_stroke=True  has_fill=False
Fill=true 无 FillColor -> has_fill=True    fill_color=(0,0,0,0) 透明
什么都不写（路径）      -> has_stroke=True  has_fill=False
什么都不写（文字）      -> has_fill=True    has_stroke=False  fill_color=黑
```

### 2. `TextCode` 的 X/Y 省略时要继承上一个（表46）

> 当 X 不出现，则采用上一个 TextCode 的 X 值，文字对象中的第一个 TextCode 的 X 属性必选。

我原来缺省一律当 0，多 TextCode 的文字会全叠到对象左上角。已改成沿用一个的 X/Y：

```
<TextCode X="5" Y="8">甲</TextCode><TextCode>乙</TextCode>
-> 甲(5,8) 乙(5,8)      # 乙 继承 甲的坐标
```

### 3. `Visible` 属性没实现（表34，默认 true）

图元对象可以有 `Visible="false"`，语义是"不绘制"。原来完全不看，被隐藏的对象照样画出来。
已在 `_emit_object` 入口跳过。

### 4. 裁剪的正确机制是 `Clips` 子元素，不是属性（表34）

我之前审计时说"ClipPath 不支持"，方向就错了。标准里裁剪是：

```xml
<ofd:Clips>
  <ofd:Clip>
    <ofd:Area><ofd:Path>…</ofd:Path></ofd:Area>
    <ofd:CTM>…</ofd:CTM>
  </ofd:Clip>
</ofd:Clips>
```

> Clip 采用**对象空间坐标系**；存在多个 Clip 时，最终裁剪区为所有 Clip 区域的**交集**。

所以正确实现是解析 `Clips/Clip`、各自转成路径、取交集，而不是读一个 `ClipPath` 属性。
这一项还没做（在下面的待办里）。

### 另外两个标准自身的矛盾，记录备查

- 表34 说图元对象 `Alpha` 默认 **0**（全透明），但颜色里的 `Alpha` 默认是 255（不透明）。
  按前者字面所有对象都不可见，显然不是本意。按实践处理：没写就是完全不透明。
- 表45 文字对象有 `FillColor` 默认黑色，但表35 图形对象 `FillColor` 默认透明——同一个
  `CT_Color` 类型，默认值取决于宿主对象，这点容易看漏。

## 三·补：结构校验（附录 A XSD）已落地

```bash
python tools/extract_xsd.py     # 从全文抽出 14 个 .xsd 到 docs/xsd/，并逐个编译
python tools/validate.py 文件.ofd [--verbose] [--strict]
```

抽取时踩到的排版问题（`tools/extract_xsd.py:fix_layout` 处理）：

- 元素名和属性名粘连：`<xs:elementname="…"` → `<xs:element name="…"`
- 引号后直接跟下一个属性：`type="ST_Box"minOccurs="0"`
- 小数点被拆行：`version="1.` + `0"`
- URL 被拆行：`"http://www.` + `ofdspec.` + `org/2016"`
- 页眉页码插在 XML 中间

还有一处**标准原文自身不一致**：正文标题写 `A.6 Definition.xsd`，但所有 schema 内部 include 的是 `Definitions.xsd`（带 s）。按 include 的实际名字落盘才能编译。

### 校验跑出来的结果

**我自己的产物**：`tools/make_sample_ofd.py` 生成的样本 6/6 条目全部通过。

**真实数电发票**：3 处不符合（都不影响阅读，阅读器宽容）：

| 位置 | 不合规点 | schema 要求 |
|---|---|---|
| `Pages/Page_0/Content.xml` | 两个 `ImageObject` **没有 `ID`** | `CT_Image` 的 `ID` 必选 |
| `Tags/CustomTags.xml` | `CustomTag` 用了 `TypeID`、缺 `NameSpace` | 要求 `NameSpace` |
| `Tpls/Tpl_0/Content.xml` | `FillColor`/`StrokeColor` 写在 `AbbreviatedData` **之前** | `CT_Path` 顺序是 `StrokeColor → FillColor → AbbreviatedData` |

这说明"能显示"和"合规"是两件事：真实文件靠阅读器宽容。所以本项目改成
**写出去的一律合规**（`ofdlite/normalize.py` + 保存时规范化）。

## 三·再补：写法约束（这条最容易被忽略）

schema 对写法有硬约束，**不是"两种写法都行"**：

| 语义 | 内部简写 | schema 唯一允许的写法 |
|---|---|---|
| 颜色 | `FillColor="0 0 0" ColorSpace="1"` 属性 | `<FillColor Value="0 0 0" ColorSpace="1"/>` 子元素 |
| 文字 | `<TextCode Text="abc"/>` | `<TextCode>abc</TextCode>` 元素内容 |
| 路径 | `<Path Data="M 0 0 L 10 0"/>` | `<AbbreviatedData>M 0 0 L 10 0</AbbreviatedData>` |

我原来为了"宽容解析"两种都读，但**写文件时用了不合规的那种**——校验器一跑全是错。
现在解析仍宽容（读得进真实文件），写出一律走 `normalize_content()` 转成合规形式。

还有两个枚举值：`ColorSpace` 的 `Type` 只能是 `GRAY`/`RGB`/`CMYK`（大写，`Gray` 不认），
`OFD.xml` 的 `Version` 固定 `1.0`（真实发票写 `1.1`，也不合规）。

## 附：生成器（tools/make_ofd.py）的逐项标准依据

生成器写出的每个字段都对应标准或附录 A 的明确规定，不是凭经验。下表是产出物与依据的对照。

| 生成器写的 | 依据 | 核对方式 |
|---|---|---|
| 页面尺寸、`PhysicalBox` | 8.x 页面区；`CT_PageArea/PhysicalBox` 为必需 | `Page.xsd` 校验通过 |
| 对象定位用 `Boundary="x y w h"` | 8.1.3 / 8.1.4：对象坐标原点在 Boundary 左上角 | 路径 `d` 从 `(0,0)` 起写 |
| 颜色写成 `<ofd:FillColor Value="r g b" ColorSpace="1"/>` 子元素 | 附录 A `CT_Color`；颜色不是属性 | XSD：写成属性会报 `attribute 'FillColor' not allowed` |
| `CT_Path` 子元素顺序 `StrokeColor → FillColor → AbbreviatedData` | `Page.xsd` 的 `CT_Path` sequence | 顺序错会被 XSD 拒绝 |
| `DashPattern` 写成属性 | **`CT_GraphicUnit` 的属性，类型 `ST_Array`**，不在 `CT_Path` 的 sequence 里 | 实测：写成子元素报 `DashPattern is not expected` |
| `LineWidth` 显式给出 | `CT_GraphicUnit` 属性，默认 `0.353` | 不写则按默认 0.353mm |
| 文字用 `<ofd:TextCode X Y>内容</ofd:TextCode>` | 表 46：X/Y 省略沿用前一个；首字必给 | 生成器首字恒给 X/Y |
| `TextObject` 的 `Font` 引用 `PublicRes` 里的 `Font ID` | 资源引用用 `ST_RefID` | XSD 校验 + 渲染可见 |
| 颜色空间在 `PublicRes` 定义 `<ofd:ColorSpace ID="1" Type="RGB"/>` | 附录 A `CT_ColorSpace`；Type 枚举只认 GRAY/RGB/CMYK | XSD |
| `Res` 根元素 `BaseLoc="Res"` | 附录 A：`BaseLoc` 为 `use="required"` | 实测：缺它会报 required |
| 图片放 `Doc_0/Res/`，登记为 `MultiMedia Type="Image"` | 资源文件约定 | XSD + 渲染可见 |
| `ImageObject` 的 `CTM="w 0 0 h 0 0"` | 纯缩放，与 Boundary 尺寸一致（见「四个错」第 4 条） | 渲染不放大 |
| `OFD.xml` 的 `Version="1.0"` | 标准规定值 | XSD |
| 路径圆角/椭圆用 `A` 弧指令（7 参数） | 表 36：`A` 后跟 7 个参数 | 渲染正确，XSD 通过 |

**校验门槛**：`python3 tools/make_ofd.py spec.json -o out/x.ofd --validate`
要求全部条目 XSD 通过（当前样本 5/5）。生成后还会过一次 `ofdlite/normalize.py`，
把任何非 schema 写法统一成规范形式。

**没做的**：`Clips` 裁剪、`Actions`、`CT_VectorG` 复用、`FixedWidth` 字宽表、
`ImageObject` 的 `Border`。这些是标准里有、生成器与渲染器都尚未支持的部分，
列在 README「已知边界」里，不假装支持。

## 附二：按 33190-2016-gbt-cd-300.pdf 复核发现的三处偏差（2026-10-29）

用用户指定的标准原件（`docs/33190-2016-gbt-cd-300.pdf`，132 页）逐条复核，发现三处与原文不一致：

### 1. 线宽下限（已修）

表21 原文：

> 由于某些设备不能输出一个像素宽度的线，因此强制规定**当线宽大于0时，无论多小都最少要绘制两个像素的宽度；当线宽为0时，绘制一个像素的宽度**。

原实现用 `max(1, round(mm × dpi / 25.4))`，0.1mm @150dpi 算出来 0.59px → 取整 1px。
现在改为 `_stroke_px()`：`w > 0` 时下限 2px，`w == 0` 时 1px。

实测影响：

```
0.1mm  @150dpi : 几何 0.59px → 标准 2px
0.05mm @96dpi  : 几何 0.19px → 标准 2px
0.353mm@150dpi : 几何 2.08px → 2px（不变）
```

真实发票渲染像素哈希改前改后一致（其线宽均 ≥0.353mm，未触发下限），
说明改动只影响原本画得过细的线条。

### 2. MiterLimit 默认值：标准正文与附录 A 互相矛盾

| 出处 | 值 |
|---|---|
| 表21 / 表35 正文 | **3.528** |
| 附录 A `Page.xsd` 的 `CT_GraphicUnit` | **4.234** |

本项目的处理：**不设默认值**（`MiterLimit` 解析为 `None`），且 Pillow 后端
不做 join 几何计算，因此该值目前只影响解析结果、不影响渲染。
Qt 与 Canvas 后端用各自图形库的默认 join 行为。

这是标准自身的矛盾，记在这里备查，不改代码去猜一个。

### 3. Alpha 默认值 0 与实际不符（有意偏离）

表34 原文：

> Alpha xs:int 图元对象的透明度，取值区间为 [0,255]，0 表示全透明，255 表示完全不透明，**默认为 0**。

若照字面执行，所有不写 `Alpha` 的对象都应是全透明，真实文档将整页空白。
本项目按 **默认 255（不透明）** 处理（`model.py` 的 `alpha()`）。

这是与标准的**有意偏离**，理由：标准此处与 255 表示不透明的定义自相矛盾，
且与实际文件的普遍写法冲突。若将来遇到确实需要"默认透明"的场景，需显式处理。

### 4. 另外确认的三处未实现（不算偏差，是缺口）

| 标准条款 | 内容 | 状态 |
|---|---|---|
| 8.2.4 | `DashOffset` 虚线起始偏移（按绘制相反方向偏移后开始） | **未实现**，只支持 `DashPattern` |
| 表34 | `Clips`/`Clip` 裁剪区，对象空间坐标、多个取交集 | **未实现** |
| 表35（图像） | `ImageObject` 的 `Border*` 系列（含 `HorizonalCornerRadius` / `VerticalCornerRadius` / `DashPattern` / `BorderColor`） | **未实现** |

顺带记下标准原文里两处容易误读的准确措辞：

- `DashPattern` 是 `ST_Array`，**两个或多个值成对解释**：第一个是实线段长、第二个是间隔长，
  以此类推（8.2.4 正文比表21 的"共含两个值"更准确）；单位 mm；
- `DrawParam` 的覆盖方向是**对象自身属性覆盖 DrawParam 里的同名字段**，
  不是 DrawParam 覆盖对象。

## 附三：裁剪区（8.4）实现要点

按 `33190-2016-gbt-cd-300.pdf` 第 53~54 页与附录 A 实现，踩到四处非查原文不可的细节：

### 1. 两层组合规则不是一回事

| 出处 | 规则 |
|---|---|
| 表34（`Clips` 属性） | 多个 `Clip` 对象 → 最终裁剪区为**所有 Clip 区域的交集** |
| 表33（`CT_Clip` 的 `Area`） | 一个 `Clip` 内多个 `Area` → 最终裁剪区是这些区域的**并集** |

实现上：并集用一场景内多条子路径的 nonzero 填充，交集用逐组累积（Pillow 用
`ImageChops.darker`，Qt 用连续 `setClipPath(IntersectClip)`，Canvas 用连续 `ctx.clip()`）。

### 2. `Actions` 与 `Clips` 必须排在派生类元素之前

`Clips` 属于基类 `CT_GraphicUnit` 的 `sequence`，而 `PathObject` 是 `extension base="CT_GraphicUnit"`。
XSD 的 extension 语义是**基类元素在前、派生类元素在后**，所以正确顺序是：

```
Actions? → Clips? → StrokeColor? → FillColor? → AbbreviatedData
```

写成 `AbbreviatedData` 之后再放 `Clips`，校验直接报
`Element 'Clips': This element is not expected.`
`normalize.py` 的元素顺序表已同步（`CT_GU_UNIT_HEAD = ["Actions", "Clips"]`）。

### 3. 裁剪区里的 `Path` 也是完整图形对象，必带 `Boundary`

`Area` 下是 `CT_Path`，它同样扩展 `CT_GraphicUnit`，`Boundary` 是 `use="required"`。
漏了会报 `Element 'Path': The attribute 'Boundary' is required but missing.`

坐标要两级叠加：`Area/Path` 的 `Boundary` 给出偏移，`AbbreviatedData` 的坐标相对这个
`Boundary`——不是直接相对外层对象的 `Boundary`。

### 4. 裁剪只作用于该图元，且对象自身 CTM 不参与

8.1.4 说「路径数据和裁剪区数据都以外接矩形的左上角为坐标原点」，两者同一坐标系。
但 8.5 的绘制顺序是「先通过外接矩形平移到对象空间，**在对象空间内根据变换矩阵和裁剪设置
进行相应绘制**」——`CTM` 作用于绘制，裁剪是在进入 CTM 之前就定好的区域。

实现上：`scene._clip_groups()` 只叠**父矩阵**，不叠对象自身 `CTM`。
把它挂到对象指令的 `clip` 字段上（而非发成独立的绘制状态），保证只有该对象被裁。

### 5. 顺带修掉的一个生成器 bug

`CT_Path` 的 `Fill` 默认值是 **false**（表35），`Stroke` 默认 true。
生成器原来只在「无填充色」时写 `Fill="false"`，有填充色时什么都不写——
结果有颜色也不填充，画出来是空白。现在有填充色时显式写 `Fill="true"`。

### 验证

```bash
# 三端渲染一致：造一个 80×40 的方块，裁剪成 30×20 + 10×20 两块
python3 tools/make_ofd.py out/clip_spec.json -o out/clip_gen.ofd --validate
#   XSD: 通过 5 / 失败 0

# 采样验证：裁剪区内为蓝色 (0,121,204)，区外与两区之间为白
#   Pillow / Qt / Canvas 三端结果一致
```

真实数电发票（不含裁剪区）渲染像素哈希改前改后一致，说明改动没有副作用。

## 附四：MiterLimit 默认值的调研（回应「参考别的项目」）

### 标准怎么说

- **表21 / 表35 正文**：「Join为Miter时小角度结合点长度的截断值，**默认值为3.528**。
  当Join不等于Miter时该参数无效」——措辞是强制性的。
- **附录 A 的 Page.xsd**：`<xs:attribute name="MiterLimit" type="xs:double" default="4.234"/>`

同一个字段两个默认值，属标准自身缺陷。

### 业界是什么值

| 来源 | 默认值 | 说明 |
|---|---|---|
| PDF (ISO 32000) | **10** | line join 的 miter limit |
| SVG 1.1 | **4** | `stroke-miterlimit` |
| MS-ODRAW | 有 `lineMiterLimit` | 微软自有格式 |
| **WPS Office 12.1** | 疑似 **3.5** | 实测其 `kufeofddom.dll` 含 `3.5f` 常量；`ksofdcore.dll` 有 `GetMiterLimit@COFD_DrawParam` 与 `GetMiterLimit@COFD_PageObject`（返回 float），但**搜不到 3.528 或 4.234 的浮点常量** |

### 一个可疑的数字关系

```
LineWidth 默认值 = 0.353 mm   （表21/表35 正文）
MiterLimit 默认值 = 3.528     （表21/表35 正文）
3.528 / 10 = 0.3528 ≈ 0.353   （差 0.0002）
```

两者正好差一个数量级。可能是起草时的笔误（小数点错位），但没有其他证据能证实。

### 本项目的取值

**按正文取 3.528**，理由：
1. 表21 是规范性条款，附录 A 是资料性附录取；
2. WPS 的 `3.5f` 常量与 3.528 吻合，4.234 在业界找不到对应；
3. 3.528 / 4.234 / 10 / 4 四家不统一，说明这个值对渲染影响有限。

### 实现与实测（诚实记录）

- 解析：`OFDObject.miter_limit()`，缺省返回 3.528
- 透传：`scene` → Qt 的 `QPen.setMiterLimit` / Canvas 的 `ctx.miterLimit`

**实测结论：三端都不产生可见效果。** 造了一份 25° 锐角的对照文件
（顶点 miter 比 = 1/sin(12.5°) ≈ 4.62，三条线分别 limit=1.5 / 3.528 / 20，
按理论 1.5 与 3.528 应截断成 bevel、20 应保留 miter 尖角），逐像素量：

| 后端 | 量法 | 结果 |
|---|---|---|
| Qt（offscreen raster） | 三条线顶点最上墨点 y | 全部相同，三条都是尖的 |
| Qt（wayland + xvfb） | 同上 | 全部相同 |
| Qt 最小例子（不含本项目代码） | 直接 `QPen.setMiterLimit(1.0…20.0)` 画一条折线 | **六种取值尖端 y 全部 = 14**，与不设时一致 |
| Canvas（Edge headless） | 三条线各自的像素高度 | **151 / 151 / 150**，无差异 |

Qt 的最小例子这条最关键：**它完全不含本项目代码，只是
`pen.setJoinStyle(Qt.MiterJoin)` + `pen.setMiterLimit(x)` 画一条折线，
结果六种 x 画出完全一样的图。** 所以这不是本项目的 bug，是 Qt（PySide6 6.x）
的 `QPen::setMiterLimit` 在 QImage 光栅渲染路径上不生效。

Canvas 那边 `ctx.miterLimit` 是 W3C 标准属性，理论上应该生效，
但实测三条线像素高度只差 1px（抗锯齿级别），也看不出 miter 延伸。

### 结论：换成「自己描边」后真正生效了

既然后端给不了，就不再依赖后端 —— 新增 `ofdlite/stroke.py`，
按标准自己把折线描边成多边形，让三个后端只做**填充**：

- `stroke_to_polygon(points, width, join, cap, miter_limit, closed)`
- 8.2.3 的判定：两段方向向量夹角 θ，miter 比 = 1/sin(θ/2)；
  超过 MiterLimit 就改按 Bevel（截断）
- 只在「实线 + Join=Miter」时走这条路，虚线仍用后端描边

实测（25° 尖角，方向向量夹角 79.6°、miter 比 1.562）：

| MiterLimit | 多边形顶点数 | 尖端相对顶点偏移 |
|---|---|---|
| 1.5 | 8 | **3.04 mm**（截断成 Bevel） |
| 3.528 | 9 | **2.05 mm**（保留 Miter） |
| 20 | 9 | **2.05 mm**（保留 Miter） |

2.05 = 4 − 1.25×1.562，与手算一致。**Qt 端渲染出来是干净的尖角，无瑕疵。**

### 试过但回退：换 Pillow 的填充内核

为了消掉下面那个小白三角，写了一份自己的扫描线填充 `ofdlite/raster.py`
（边表 + 活动边，支持 nonzero / evenodd，两种 fill rule 都用「外框+内框」
的对照用例验过：同向 nonzero 填、反向 nonzero 空、两种 evenodd 都空）。

接进 `PilRenderer._draw_path` 之后**底纹的 6 项检查挂了 4 项**——底纹单元
本身也要走填充，换了内核后单元内容画不出来。判断：小白三角只是视觉瑕疵，
底纹整体失效是不可接受的回归，所以**回退了 Pillow 的填充改动**，
`raster.py` 作为独立模块保留（算法本身是对的，将来接别的后端能用）。

这件事的教训记在这里：换渲染内核要一次换彻底（连同底纹、渐变、图像蒙版
一起验），只换「路径填充」这一小块，会把依赖同一填充路径的其它功能带崩。

### 剩余瑕疵（如实记）

Pillow 后端在尖角内侧会露出一个小白三角：它用 `ImageDraw.polygon` 填充，
对自交多边形没有 nonzero/evenodd 的选择，而 Qt 与 Canvas 走 nonzero 是正确的。
影响范围仅限「Pillow 导出的实线 Miter 尖角」，视觉上是个小缺口。

修法有二：把多边形做凸分解后逐块填，或 Pillow 端改用自带扫描线填充；
两条都要改渲染内核，暂记为已知瑕疵。

### 许可与专利

- **Cairo**：LGPL-2.1 / MPL-1.1 **双许可**（本机 `/usr/share/doc/libcairo2/copyright` 原文）。
  deb 里作为 `Depends: python3-cairo` 引用系统库、不打包源码不修改 → 不触发传染。

- 真正的专利风险在**标准本身**（GB/T 33190-2016 前言自认「可能涉及专利」），

（文字排版、图像缩放、蒙版合成、渐变、底纹全要重做），不是小改动。
是否移植由需求决定，可行性已验证通过。

## 附六：自带依赖（vendor）方案与当前进度

### 为什么要自带

目标机是银河麒麟，可能没网、装不了 `python3-pil` / `python3-cairo`。
自带依赖 = deb 里直接带 Python 模块与它们依赖的 .so，启动脚本改 `PYTHONPATH` + `LD_LIBRARY_PATH`。

### 实测体积

| 项目 | 体积 |
|---|---|
| Pillow（模块 + C 扩展） | 6.7 MB |
| pycairo（模块 + `_cairo` 扩展） | 0.4 MB |
| 已收集的 .so（18 个） | 4.4 MB |
| **合计** | **约 13 MB**（当前 deb 是 145 KB） |

### 绝不能自带的

| 库 | 原因 |
|---|---|
| `libc.so.6` / `libm.so.6` / `libpthread.so.0` | glibc 系列。`LD_LIBRARY_PATH` 优先级高于系统路径，带上会加载到假 libc，**python3 自己都起不来**（实测报 `GLIBC_2.38 not found`） |
| `libfreetype.so.6` / `libfontconfig.so.1` | 字体发现必须读系统 fontconfig 配置，自带会成为孤岛，看不到系统字体 |

### 踩到的两个坑

1. **Ubuntu 的 symbol versioning**：`ldd` 报 `libtiff.so.6`，实际文件名是
   `libtiff-20b7e810.so.6.3.0`。必须拷真实文件 + 按 `DT_NEEDED` 的名字建符号链。
2. **glibc 链接污染**：第一版 `fill_needed_links` 没过滤 glibc，在 `vendor/lib` 里
   建了 `libc.so.6` 链接，结果 `LD_LIBRARY_PATH` 让 python3 加载到假 libc，直接崩。
   现在过滤了，`vendor/lib` 里确认没有 glibc。

### 当前状态：已完成，包从 145 KB 增到 7.7 MB

修掉两个根本问题后就通了：

1. **`ldd` 换成 `readelf -d`**：`ldd` 在 `vendor/python/PIL/` 这种目录下对
   `_imaging.so` 全报 `not found`（`libtiff` / `libjpeg` / `libopenjp2` 都解析不出），
   收集器直接拿到空列表。`readelf -d` 只读 ELF 头的 `DT_NEEDED`，不受运行环境影响。

2. **发现 pip wheel 的 `.libs` 目录**：Pillow 的 C 扩展 `RPATH` 是
   `$ORIGIN/../pillow.libs` —— pip 的 manylinux wheel 把 18 个依赖库
   （tiff/jpeg/openjp2/webp/zstd/lzma/Lerc/jbig/deflate/imagequant/avif/harfbuzz/
   freetype/lcms2/brotli/sharpyuv/xcb/Xau）全放在同级 `pillow.libs/` 里，靠 RPATH 找。
   **不用逐个收集，整目录拷过去就行。** 且目录名不等于模块名（模块 `PIL`、目录
   `pillow.libs`），不能靠猜名字，要扫同级所有 `*.libs`。

于是 `vendor_deps.py` 的真正职责简化成两件事：拷 Python 模块 + 拷同级 `*.libs`；
再补上 cairo 那条链（pixman/brotli/expat/bz2/bsd/md/X11 等 14 个 .so，4.0 MB）。

### 体积

| 项目 | 体积 |
|---|---|
| `vendor/python/pillow.libs`（Pillow 的 wheel 库） | 14.0 MB |
| `vendor/python/PIL`（模块） | 6.7 MB |
| `vendor/python/cairo`（模块） | 0.4 MB |
| `vendor/lib`（cairo 链，14 个 .so） | 4.0 MB |
| **解包后** | **26 MB** |
| **deb（xz 压缩）** | **7.7 MB** |

## 附七：纯 Python 渲染后端（不用 Pillow）

按项目原则「能自己写的对照标准自己写实现」，把渲染拆成四个自己写的模块：

| 模块 | 职责 | 对应标准 |
|---|---|---|
| `ofdlite/raster.py` | 扫描线多边形填充，nonzero / evenodd | 9.2 填充规则 |
| `ofdlite/stroke.py` | 折线转多边形描边，miter 截断、cap 三档 | 8.2.2 / 8.2.3 / 8.2.5 |
| `ofdlite/pngcodec.py` | PNG 编码（IHDR/IDAT/IEND + CRC32）与解码（五种滤波） | ISO/IEC 15948 |
| `ofdlite/render_soft.py` | 画布（RGBA bytearray）+ 指令分派 + 导出 | 第 8 章图形 |

**没有任何一处依赖 Pillow**：实测渲染前后 `'PIL' in sys.modules` 始终为 False。

### 实测性能

| 场景 | 像素 | 耗时 |
|---|---|---|
| 测试图 709×531 | 37 万 | 0.18 秒 |
| A4 @150dpi 1240×1754 | 217 万 | 1.06~1.17 秒 |

扫描线只在对象包围盒内做，水平跨段用切片赋值，不是逐像素。

### PNG 编解码正确性

- 编码 → 自己解码：像素完全一致
- 编码 → Pillow 解码：能读，尺寸与首像素都对（证明符合 ISO/IEC 15948，
  不是自说自话）

### 当前覆盖与缺口

| 能力 | 状态 |
|---|---|
| rect / path 的填充（含 fill rule） | ✅ |
| path 的描边（miter 截断 / round / bevel / cap 三档） | ✅ |
| PNG 编解码 | ✅ |
| **渐变**（轴向/径向/高洛德/网格） | ✅ 已接（三端里唯一四类全支持的） |
| **裁剪**（Clips） | ✅ 已接（组内并集、组间交集） |
| **虚线**（DashPattern/DashOffset） | ✅ 已接（含相位偏移与三段图案） |
| **文字**（TrueType 光栅化） | ✅ 已接（自写 TTF 解析 + 轮廓提取） |
| **图像资源**（贴图与合成） | ✅ 已接（含 1/2/4 位深度与调色板 PNG） |

缺口都在告警里明说，不静默丢弃——导出图缺字时用户能立刻看到原因。

### 图像贴图（10 章）

- 资源来自 `scene.resources`，是 base64 的 PNG；按 `res_id` 缓存解码结果，
  同一张图被多个 ImageObject 引用时只解一次
- 落位用 `Boundary`（对应 op 的 x/y/w/h），按目标像素尺寸从源图采样
- 合成：RGBA 走 source-over（按 `Alpha` 与源 alpha 相乘），灰度/双通道按各自语义展开
- **PNG 解码补了低色深**：1/2/4 位要按位拆包，且滤波用的 bpp 是
  「一个像素占几个字节」（低色深时按 1 算），不是「每行字节数」
  —— 这两点搞错就是花屏。调色板（color type 3）也补了。

实测真实数电发票（1240×827 @150dpi，0.73 秒）：二维码（1 位深度）、
监制章（RGBA 650×433）、框线全部正确，只剩文字缺失（告警已说明）。

### 为什么这条路的收益不只是「不用 Pillow」

Pillow 的 `ImageDraw` 表达不了 OFD 要求的几件事，实测过的：
- `MiterLimit` 完全不生效（Qt 也一样，见附四）
- 没有 fill-rule 参数，自交轮廓会挖白洞
- `joint` 只有圆角，Miter / Bevel 只能近似

自己写之后这些语义都能按标准落到底。

## 附九：文字渲染（自写 TrueType 解析）

### 为什么自己写

用户原则：能自己写的对照标准自己写。freetype / fontTools 都能给出轮廓，
但那样「字符 → 轮廓」这一步就交给别人了。OpenType/TrueType 的 glyf 表
规范清楚，自己写完全可控，也不必给麒麟端再加一个 .so。

### 新增两个模块

**`ofdlite/ttf.py`** —— TrueType 解析与轮廓提取
- 表目录解析，支持 `ttcf` 字体集合（取第一个子字体；Linux 中文字体常是 .ttc）
- `head`（unitsPerEm / indexToLocFormat）、`maxp`（numGlyphs）、
  `hhea`（numberOfHMetrics）、`hmtx`（advanceWidth）
- `cmap` 的 format 4（BMP）与 format 12（全 Unicode），按 (3,10) > (3,1) > 0/x 优先
- `loca` + `glyf`：简单字形（重复标志、短/长向量、on/off-curve）与

  TWO_BY_TWO、MORE_COMPONENTS，递归展开）
- 二次贝塞尔压平：按 TrueType 规则处理「两个相邻 off-curve 之间隐含中点」、
  全 off-curve 轮廓用首尾中点当起点

**`ofdlite/fontfind.py`** —— 字体名到文件的映射
- 直接读 TTF 的 `name` 表（家族名 / 全名 / PostScript 名），不解析 fontconfig
  的展示字符串——那种输出人看得懂，程序解析起来脆
- 内置别名表把 OFD 常见字体名映射到本机字库（宋体→SimSun/Noto Serif CJK、
  黑体→SimHei/文泉驿微米黑、楷体→KaiTi/AR PL UKai、Courier New→Nimbus Mono…）
- **排除斜体/粗体变体**：同一家族名可能对应多个文件，先到先得会把
  `NimbusMonoPS-Italic` 选进来（实测踩过），变体名加 `~` 前缀放冷宫
- 都找不到时兜底到全覆盖中文字体（Droid Sans Fallback 等）

### 渲染

`render_soft._text()`：字形轮廓 → 按 `size / unitsPerEm` 缩放 → y 取反
（字体 y 向上、页面 y 向下）→ 平移到基线起点 → 用同一套扫描线填充。
`hscale`、`spacing`、每个字符的 `advance` 都按标准处理。

- **坐标单位**：scene 给的渐变几何是 mm，着色时用像素坐标，
  必须先乘 k 换算——不换算色带位置全错（实测：第一条渐变只剩左边一小条）

## 附十一：抗锯齿（自己实现，不用任何后端的 AA）

### 算法

`raster.fill_coverage()`：返回**每像素覆盖率（0~255）**而不是 0/1 掩码。

两个方向用不同手段，比 4×4 全超采样省很多次求交：

| 方向 | 做法 |
|---|---|
| 垂直 | 抽 `ss` 条子扫描线（`y + (k+0.5)/ss`），结果平均 |
| 水平 | 不算采样点，直接算 span 与像素的**精确重叠长度** |

两者相乘得到覆盖率，填充时按覆盖率折算 alpha 混合。

### 实测

斜三角形，y=30 处左边落在 x≈18.1：

```
ss=1  x16..21 = [0, 0, 175, 255, 255, 255]
ss=4  x16..21 = [0, 0, 175, 255, 255, 255]
0/1   x16..21 = [0, 0, 255, 255, 255, 255]     ← 原来边缘是硬跳变
```

边缘像素从 255 变成 175，就是亚像素覆盖的体现。y=31 时是 71，同样符合
「左边在 x≈18.5」的几何预测。

### 性能

| 配置 | A4 @150dpi（217 万像素） |
|---|---|
| 无抗锯齿（ss=1） | 约 1.2 秒（改造后 3.0 秒，见下） |
| ss=4（默认） | 2.87 秒 |
| 只优化前 | 4.82 秒 |

中间做过一次优化：原来是逐像素算「span 与像素的重叠」，改成
「整像素区间批量累加 + 只有两个端点算小数」，4.82 → 2.87 秒。

**已知**：ss=1 和 ss=4 现在速度接近（2.9~3.0 秒），说明还有别的固定开销
（每行 `[0.0] * width` 的分配、写回 cov 的循环）。没有继续优化——2.9 秒
导出一页 A4 在可接受范围，继续抠这个的收益不如补功能。

### 接进渲染

- `SoftRenderer(dpi, ss=4)`，`render_page(page, dpi, ss)`
- `Canvas.fill_polygons(..., ss=4)`
- 覆盖率 ≠ 255 时按 `fa = (cvr/255) * a` 折算后做 source-over

文字、椭圆、对角线全部获得平滑边缘（对比附九的硬边图很明显）。

### 偏离二：Extend 的语义

> Extend：轴线延长线方向是否继续绘制渐变。可选值为 0、1、2、3
> 0: 不向两侧继续绘制渐变

> 2: 在起始点至结束点延长线方向绘制渐变

原文还说：Extend≠0 且 MapType=Direct 时，延伸区域用「该方向轴点所在的段的颜色」。

**我原来的实现**：对 t 一律 clamp 到 [0,1]，等于无条件按 Extend=3 处理。
`Extend=0` 时轴外应该是**透明不画**，我却填了端点色。

| 3 | 红 ✓ | 渐变 ✓ | 蓝 ✓ |

**修后**：周期性判断 `k = floor(t/period)`，`k` 为奇数时 `tt = 1 - tt`。

### 补 Weight（表 45）

标准：`Weight` 取值 100/200/300/400/500/600/700/800/900，默认 400。

原来只做了布尔：`Weight >= 600` 就算粗体，中间档全被压成「正常」或「粗」两档。
现在按档位给不同加粗量（`size` 的比例）：

| Weight | 加粗比例 |
|---|---|
| 400 | 0（不加） |
| 500 | 0.012 |
| 600 | 0.022 |
| 700 | 0.035 |
| 800 | 0.046 |
| 900 | 0.058 |

非标准值按最近的 100 取整，<100/>900 夹到边界。

|---|---|
| 400 | 104842 |
| 500 | 107857 |
| 600 | 109272 |

### 补图片双线性采样

原来是最近邻，放大时锯齿明显（监制章那种细线条最看得出来）。

改成四邻域双线性：源坐标保持浮点，按 `(1-wx)(1-wy)` / `wx(1-wy)` / `(1-wx)wy` / `wx·wy`

三处偏离全部修掉并实测验证；一处新缺口（Weight）如实记下。

## 附十三：CFF（Type2 charstring）——标准要求，不是可选项

### 依据

GB/T 33190-2016 表 44：

> **FontFile** —— `ST_Loc`，指向内嵌字型文件，**嵌入字型文件应使用 OpenType 格式**

OpenType 容器有两种轮廓：
- `glyf` 表（TrueType 轮廓，二次贝塞尔）
- `CFF ` 表（Type2 charstring，三次贝塞尔）

之前只做 glyf，遇到 `.otf`（思源系列、部分 Noto CJK）只能告警退到兜底字体。
按标准口径这是**不完整**，所以必须补。

### 新增 `ofdlite/cff.py`

| 部分 | 内容 |
|---|---|
| INDEX | Name / TopDICT / String / GSubr / CharStrings，1~4 字节偏移都支持 |
| DICT | 整数（28/29）、实数（30）、单双字节操作数；`12 xx` 转义运算符 |
| Private | `defaultWidthX`(20) / `nominalWidthX`(21) / `Subrs`(19) |
| Type2 | rmoveto / hmoveto / vmoveto、rlineto / hlineto / vlineto、rrcurveto、rcurveline / rlinecurve、vvcurveto / hhcurveto、vhcurveto / hvcurveto、flex / hflex / hflex1 / flex1、callsubr / callgsubr / return / endchar、hintmask / cntrmask / hstem / vstem |
| 细节 | subr 的 bias（<1240 时 107、<33900 时 1131、否则 32768）、charstring 开头的可选 width 操作数、hintmask 后按 `(nstems+7)//8` 跳过 hint 字节 |

### 接进 `ttf.py`

`Font.__init__` 里若发现 `CFF ` 表，就构造 `cff.CFF`；此时跳过 `loca` 解析，
字形数改从 CharStrings 取。`glyph_outlines()` 分流到 CFF 分支，
并按 FontMatrix 换算到 font units：

```
scale = 1 / (FontMatrix[0] * units_per_em)
```

### 实测

```

   A gid=34 轮廓=2 点=99
   中 gid=0 轮廓=0 点=0        ← 该字体没有中文，正常

DroidSansFallbackFull.ttf  glyf upem=256 glyphs=49382 cmap=28601
   A gid=0 轮廓=2 点=10
   中 gid=7109 轮廓=3 点=27
```

衬线、字距全部正确——**点数够不代表形状对，必须画出来看**。

### 还没做的

| 项 | 影响 |
|---|---|
| CFF2（可变字体） | 现代 Noto 可变字体是 CFF2，会告警 |
| seac 组合字符 | 极少见，遇到会缺笔画 |
| hint 的实际作用 | 压平轮廓时不需要，不影响形状 |

### 验证方法上的一个教训

`glyph_outlines()` 返回非空、点数够，**不等于形状对**。点数只能证明

这条对 CFF 尤其重要——Type2 是堆栈式语言，栈错位一位就整条路径歪掉，
但点数照样正常。

## 附十四：图片的非轴对齐变换（CTM 旋转/斜切）

### 问题

原来 `_image` 只用 `x/y/w/h` 画轴对齐矩形。OFD 的 ImageObject 用 `CTM`
（仿射变换）定位，`Boundary` 只是未变换时的落位。带旋转/斜切的图片
原来只告警、照轴对齐画——图会错位。

### 做法

仿射变换把矩形映射成**平行四边形**，所以：

```
P = P0 + s·u + t·v       u = P1 - P0,  v = P3 - P0
```

对目标包围盒内每个像素，解 2×2 线性方程得 `(s, t)`；落在 `[0,1]²` 内的
就是图内点，再乘源图尺寸做双线性采样。行列式：

```
det = u.x·v.y − u.y·v.x
```

`|det| < 1e-12` 说明四边形退化成线，跳过并告警。

新增 `ofdlite/imgquad.py`：`quad_inverse` / `bbox_of` / `sample_bilinear` /
`is_axis_aligned`。轴对齐时仍走原来更快的矩形路径，只有非轴对齐才走这条路。

### 实测

造三种变换对照（`out/imgrot3.ofd`，200dpi）：

| # | CTM | corners（mm） | 结果 |
|---|---|---|---|
| 1 | `1 0 0 1 20 20` | (20,20)(60,20)(60,50)(20,50) | 轴对齐矩形 ✓ |
| 2 | `0.866 0.5 -0.5 0.866 100 30` | (100,30)(134.6,50)(119.6,76)(85,56) | **旋转 30°** ✓ |
| 3 | `1 0.5 0 1 30 90` | (30,90)(70,110)(70,140)(30,120) | **斜切平行四边形** ✓ |

三种无告警，形状与 corners 完全一致。

### 踩的坑：CTM 的平移是绝对量

第一次构造测试文件时，我按「Boundary 定位 + CTM 绕 Boundary 转」理解，
写 `Boundary="100 20 40 30"` + `CTM="... 110 30"`，结果 corners 跑到
(186, 97) 到 (221, 143)，页面外。

实际是：`CTM` 会把 **Boundary 的坐标一起变换**，
所以 `corners[0] = CTM.apply(boundary.x, boundary.y)`。
要定位到哪里，就得用 `Boundary="0 0 w h"` + 在 CTM 的 e/f 里给绝对平移。

这条对**写测试文件**的人很重要——测试文件构造错了，会误判实现有 bug。

## 附十五：纯 Python 底纹（8.3.3 / 表 28）

### 标准要点（原文）

| 属性 | 规定 |
|---|---|
| Width / Height | 单元宽高 |
| XStep / YStep | **若设定值小于单元的宽度/高度，应按默认值处理**（默认 = 单元宽高） |
| ReflectMethod | 枚举 `Normal` / `Column` / `Row` / `RowAndColumn`，默认 Normal |
| RelativeTo | `Page`（页面原点）/ `Object`（对象原点），默认 Object |
| CTM | 先做 XStep/YStep 排列，**然后整体做 CTM** |
| CellContent | 单元内容，**独立坐标空间**：左上角 (0,0)、X 右、Y 下、单位毫米 |

### 实现

```
_pattern_tile()   把 CellContent 渲染成一张 RGBA 贴图（按 w×h 建临时画布）
_fill_pattern()   按 XStep/YStep 平铺 + ReflectMethod 镜像 + 掩码裁形
```

按表 28 的顺序：

1. 渲染单元（独立坐标空间，与对象无关）
2. `xstep = max(XStep, Width)`、`ystep = max(YStep, Height)`——照原文的「小于就按默认处理」
3. 平铺时用 `gx = floor((x - ox) / stepx)` 算格号，`gx` 为奇数且 ReflectMethod 含
   `column` 就左右翻；`gy` 为奇数且含 `row` 就上下翻
4. 用同一套扫描线覆盖率掩码裁到对象轮廓内（所以底纹只出现在图形内部）

### 实测

`out/pt_test.ofd`（8×8mm 单元、10mm 步长、RowAndColumn）：

逐格红块中心颜色一致，镜像后红块仍在格内（说明翻转没把内容翻出去）。
渲染图 `out/pt_soft.png` 与 Pillow 后端视觉一致。

### 一个已知近似

`RelativeTo=Object` 时，标准说「相对于**对象坐标系的原点**」，即 Boundary 的左上角。
`_path` 拿到的 polys 是绝对坐标，没有 Boundary 信息，所以用**对象包围盒左上角**近似。

差异只在「对象有描边外扩、包围盒大于 Boundary」时出现，偏移量等于半个线宽。
真要做准得让 scene 把 Boundary 一起传给渲染器。记在这里，不假装精确。

## 附十八：拿 WPS 导出的真实文件做真值，查出三个真 bug

用户提供 `市场运营部 2026年第三季度工作总结.ofd`（WPS 10 页导出，4 个内嵌 TTF、
2 张 JPEG、539 个 TextObject）。用它对照，查出三处真问题。

### bug 1：CTM 与 Boundary 的关系，两种写法并存

**表 34 原文**：
> Boundary —— 外接矩形，采用**当前空间坐标系**（页面坐标或其他容器坐标），
> 当图元绘制超出此矩形区域时进行裁剪
> CTM —— **对象空间内**的图元变换矩阵

两派实现都存在，都有真实文件在用：

| 写法 | 公式 | 实测来源 |
|---|---|---|
| std | `CTM.apply(Boundary.xy + p)` | 数电发票（政务系统） |
| bound | `CTM.apply(p) + Boundary.xy` | **WPS 导出** |

单位 CTM 时两者完全相同，无法区分；但 WPS 用
`CTM="0.3528 0 0 -0.3528 0 297.0223"`（含 y 翻转），按 std 会把 f 平移吞掉：

```
路径点 (0, 841.9)，Boundary=(25.4545, 174.442)
std  : CTM.apply(25.4545, 1016.342) = (8.98, -61.54)   ← 跑到页面外
bound: CTM.apply(0, 841.9) + B.xy   = (25.45, 174.46)  ← 正确
```

**做法**：`_pick_map_mode()` 两种都算，取「包围盒与 Boundary 重叠更大、
超出更少」的那个。判据来自表 34 本身——Boundary 就是外接矩形，
正确映射后的包围盒理应贴合它。

改完必须同时验两边：数电发票 6.1%、WPS 4 页 3.9/0.9/5.0/3.8%，都无告警。

### bug 2：内嵌字体没被用上

`scene` 只传了字体名（`SimSun`、`TimesNewRomanPS-BoldMT`），渲染器只能去系统
字库里找，找不到就兜底到中文字体——**字形和原文档不一致**。

标准表 44 有 `FontFile`（指向包内 ttf/otf）。补：`FontSpec.owner` 是 `PublicRes`
（`font_file_entry` 在它上面，不在 Document 上），拿到路径后 `pkg.read()` 读字节。

### bug 3：内嵌子集字体没有 cmap，必须用 CGTransform

WPS 的内嵌字体是**子集字体**，`cmap` 表可以不存在。第一版直接报「缺 cmap 表」
跳过了全部文字。

**表 48 / 11.4 的 CGTransform 就是干这个的**——它直接给「字符编码 → 字形索引」：

```xml
<ofd:CGTransform CodePosition="0" CodeCount="5" GlyphCount="5">
  <ofd:Glyphs>5170 3434 17920 14933 18200</ofd:Glyphs>
</ofd:CGTransform>
```

补：`ttf.py` 允许 cmap 缺失（置空不报错）；`scene` 把 Glyphs 摊平带进 text op
（整体绘制带 `glyphs` 列表、逐字符带 `glyph` 单值）；渲染时优先用索引，
没有才回落 `cmap`。

### JPEG 解码（已补）

第 2 页两张 JPEG（1812×1062，SOF0 基线、4:2:0），补完 `ofdlite/jpeg.py` 后
那页非白像素从 **0.9% → 6.1%**，柱状图与坐标文字全部正确。

实现链：DQT → DHT → SOF0 → SOS → Huffman（DC 差分 + AC 的 EOB/ZRL）→
反 zigzag → 反量化 → 分离式 IDCT → 4:2:0 上采样 → YCbCr→RGB。

两个踩到的点：

1. **DC 差分是按分量累加的** —— 每个分量的 predictor 独立，块重置时要清零。
2. **只有 DC 的块可以跳过 IDCT**：IDCT 退化成「DC/8 + 128」的常数填充。
   图表、纯色背景这类图片里绝大多数块都是这样，加上这个短路后
   单张 1812×1062 从 **10.6 秒降到 3.53 秒**。

改完跑了全套：selftest 20/20、web_test 21/21、real_sample 6/6、qt_smoke 12/12、
full_check 全部达标、xcheck 像素级通过、底纹 6/6。

## 附十九：JPEG 基线解码器（ISO/IEC 10918-1）

### 为什么自己写

标准第 10 章不限定图片格式（`MediaFile` 只写文件名），JPEG 是实际最常见的
一种，WPS 导出的真实 OFD 就用它。之前只有 PNG 解码器，那一页只剩文字。

### 覆盖

| 部分 | 内容 |
|---|---|
| 标记 | SOI / APPn / DQT / DHT / SOF0 / SOS / DRI / EOI |
| 精度 | 8 位，三或单分量 |
| 采样 | 任意因子（1×1 / 2×1 / 1×2 / 2×2），实现了通用上采样 |
| 熵解码 | Huffman：DC 差分 + AC 的 EOB(0x00) 与 ZRL(0xF0) |
| 变换 | 反 zigzag → 反量化 → 分离式 2D IDCT |
| 色彩 | YCbCr → RGB，单分量走灰度 |
| 重启 | DRI/RSTn（代码路径在，但真实样本没触发过） |

**不做**：渐进式（SOF2）、无损（SOF3）、算术编码 —— 遇到会明确报
「只支持基线 JPEG…未实现」而不是解出坏图。

### 两个关键细节

**1. DC 差分按分量独立累加**

每个分量的 DC predictor 是分开的；遇到重启标记时所有 predictor 归零。

**2. 只有 DC 的块可以短路**

`_decode_block` 里记一个 `nonzero` 标志，AC 全 0 时 IDCT 退化成常数：

```
像素值 = clamp(round(DC/8 + 128))
```

图表、纯色背景这类图片绝大多数块都命中这条，实测单张 1812×1062：

| 版本 | 耗时 |
|---|---|
| 无短路 | 10.63 秒 |
| **加短路** | **3.53 秒** |

### 正确性验证

不是只看「解出来不报错」，而是把两张图解成 PNG 之后肉眼核对：
柱状图的柱子位置、颜色、纵轴刻度、中文标签全部正确 ——
说明 Huffman、反量化、IDCT、4:2:0 上采样、YCbCr→RGB 每一环都对。

### 代价

单张 1812×1062 约 3.5 秒。这是纯 Python 做 30K 个 8×8 IDCT 的必然结果。
真要更快得上 numpy 或换 C，但那会破坏「纯 Python 无第三方依赖」这条线，
所以先接受。渲染时可以按 dpi 降采样显示，导出才用原图。

### 现状

接入 `render_soft._decode_image`：PNG 走 `pngcodec`，JPEG 走 `jpeg`，
靠文件头 `\x89PNG` / `\xff\xd8` 分流。

WPS 那份文件现在四页非白像素 3.9% / **6.1%** / 5.0% / 3.8%，全部无告警。

### 优化一：轴对齐矩形走快速路径（有效）

## 附二十五：表 21 线宽下限（对照标准查出一处真偏离）

### 原文

> **LineWidth** —— 线宽，非负浮点数…由于某些设备不能输出一个像素宽度的线，因此
> **强制规定当线宽大于 0 时，无论多小都最少要绘制两个像素的宽度；当线宽为 0 时，

> 默认值为 0.353mm

### 查出来的偏离

**1. scene 层把 0 吃掉了**

```python
"w": round(max(w, 0.05), 4)     # 原来
```

线宽 0 被硬抬成 0.05，标准里「w=0 画 1 像素」这条语义直接消失。
改成原样传 `max(w, 0.0)`，下限交给渲染器按像素算。

**2. 渲染层根本没有下限**

```python
w = float(op.get("w") or 0.2) * k     # 原来
```

两个问题：
- `0 or 0.2` 把 0 变成 0.2（Python 的 falsy 陷阱）
- `w>0` 时没有任何「最少 2 像素」保护

### 修法

下限必须按**像素**算，不能按 mm —— 同一个 0.05mm 在 72dpi 和 600dpi 下
占的像素数完全不同：

```python
if w_mm <= 0.0:
    w = 1.5 / k          # 标准说 1 像素，实际给 1.5
else:
    w = max(2.5 / k, w_mm)   # 标准说 2 像素，实际给 2.5
```

**为什么给 1.5 / 2.5 而不是 1 / 2**：扫描线是隔一整行采样的（`y + 0.5`），
恰好 1 像素宽的多边形在部分 dpi 下只盖住半个采样点。这是工程取舍，写在代码注释里。

### 实测（`out/lw_test.ofd`，三条 LineWidth=0 / 0.05 / 1.0 的线）

| dpi | w=0 | w=0.05 | w=1.0 |
|---|---|---|---|
| 72 | 2 行 | 1 行 | 3 行 |
| 150 | 1 行 | 1 行 | 7 行 |
| 600 | **0 行** | 2 行 | 24 行 |

### 已知限制：`w=0` 在超高 dpi 下画不出

查清了根因：`w=0` 时 scene 走的是「不转多边形」分支，渲染器只拿到一条**线段**
（2 个点），而 `w>0` 的线是已经转成四边形的 `fill`。
线段路径在 600dpi 下（1.5 像素宽）没能产生覆盖率。

**没有继续修的原因**：标准自己写了「由于线宽 0 的定义与设备相关，所以
**不推荐使用线宽 0**」。真实文件（数电发票、WPS 导出）里没有一条 `LineWidth=0`
的线。为一个标准明确不推荐的取值去改描边路径，风险大于收益。

如实记在这里，不算"已完成"。

## 附二十六：表 30 径向渐变 —— 查出三处偏离

### 原文

| 属性 | 说明 |
|---|---|
| `Eccentricity` | 两个椭圆的离心率（焦距/长轴），[0, 1.0)，**默认 0（椭圆退化为圆）** |
| `Angle` | 两个椭圆的倾斜角度，**椭圆长轴与 x 轴正向的夹角**，单位度，默认 0 |
| `StartPoint` / `EndPoint` | 起始椭圆 / 结束椭圆的**中心点** |
| `StartRadius` / `EndRadius` | 起始 / 结束椭圆的**长半轴**（不是半径） |
| `MapType` / `MapUnit` / `Extend` / `Segment` | 与轴向渐变同构 |

### 我原来的实现（三处都错）

```python
cx, cy = shd["start"]                  # ← EndPoint 被完全忽略
d = math.hypot(x - cx, y - cy)         # ← 只会画圆，Eccentricity/Angle 没用
t = (d - r0) / (r1 - r0)
```

1. **`Eccentricity` 和 `Angle` 完全没用** —— 标准说这是**两个椭圆**，我画的是圆
2. **`EndPoint` 被忽略** —— 两个中心点可以不同，我当成同心
3. **半径是「长半轴」** —— 圆的时候两者相等所以看不出，椭圆时要用 `b = a·√(1-e²)`

### 正确做法

求 `t` 使点 `P` 落在「起点椭圆与终点椭圆的插值椭圆」上：

```
|P − t·Q| = r0 + t·(r1 − r0)          Q = EndPoint − StartPoint
```

先把 P、Q 转到起点坐标系并按 `1/√(1-e²)` 压扁 y（椭圆 → 圆），再解这个二次方程：

```
A = |Q|² − dr²
B = −2(P·Q) − 2·r0·dr
C = |P|² − r0²
```

### 踩的坑：同心时二次方程退化

`Q = 0` 且 `r0 = 0` 时，`A = −dr²`、`B = 0`、`C = |P|²`，
解得 `t = 0` —— **整个渐变画成最外圈一个颜色**。

而 `r0 = 0` 正是最常见的径向渐变写法（从点发散）。

补同心分支：

```python
if |Q|² < 1e-12:
    d = |P|
    t = (d − r0) / dr        # 同心时就是到中心的距离
```

### 验证

**同心圆**（`start=end=(70,24)`，`radii=[0,19]`，`ecc=0`，黄→蓝）：

| 距中心 | 颜色 |
|---|---|
| 0.0mm | (253, 253, 2) |
| 5.0mm | (188, 188, 67) |
| 10.0mm | (123, 123, 132) |
| 15.0mm | (54, 54, 201) |
| 18.5mm | (9, 9, 246) |

线性过渡 ✓

**椭圆**（长半轴 20mm、`ecc=0.8` → 短半轴 `20·√(1−0.64) = 12mm`）：

| 位置 | 颜色 | 说明 |
|---|---|---|
| 沿 x 20mm | (0,0,255) | 长轴边界，已到终点色 ✓ |
| 沿 x 12mm | (102,0,153) | 中途色 ✓ |
| 沿 y 12mm | (0,0,255) | **短轴边界**，已到终点色 ✓ |
| 沿 y 20mm | (0,0,255) | 超出短轴 ✓ |

**y 方向 12mm 就到边界**，正是短半轴该有的值 —— 压扁生效。

**我把「复合对象」当成了「组对象」**——以为内容是 XML 子元素。

实际上内容是**外部资源**（`CompositeGraphUnit`），`ResourceID` 指向它。
真正的复合对象在我这套实现下**一个像素都画不出来**，因为它的 XML 里没有子元素。

### 补的东西

1. `PublicRes` 解析 `CompositeGraphUnit`：`Width`/`Height`/`Content`/`Thumbnail`/`Substitution`
2. `Document.find_vectorg(id)`
3. `CompositeObject.resource_id()` / `vector_g()` / `content_objects()`
4. `children()` 优先走 ResourceID 的内容，没有才退回 XML 子元素（兼容非标准写法）
5. `scene` 里给复合对象的内容补上 `Boundary` 原点平移与自己的 CTM

### 顺带修的：`Layer.flat_objects()` 重复展开

补完第 4 步后，`flat_objects()` 把复合对象的子对象也拍平了一遍，
而 `_emit_object` 对 `CompositeObject` 又展开一遍 —— **同一份内容画两遍**，
其中一遍没有 Boundary 偏移，画在 (0,0)，把正确的那份盖住了。

修：`flat_objects()` 遇到 `CompositeObject` 不再展开（它的内容必须由
`_emit_object` 带偏移处理）。

修完实测 `out/cg2_test.ofd`（矢量图像 20×20，含一个 40×4 的溢出红条，
复合对象 `Boundary="30 30 20 20"`）：


### 未实现：`Width`/`Height` 的裁剪

表 50 明说「超出部分做裁剪处理」。我试过挂 `clip`，但**挂上去会把内容整块裁空**：

```python
it["clip"] = [clip_rect]     # clip_rect = [_flat]
```

`clip` 的正确结构是 `[组[子路径[扁平坐标]]]`，`_clip_groups` 那边上一轮又改成了
接受 `(ClipCTM, 子路径)` 二元组 —— 两边的层次没对齐，裁出来的区域是空的。

**最后修好了，真正的 bug 不在形状，在临时画布的偏移**。

先按 `_render_clipped` 的实际遍历反推形状，手工喂三种结构：

| 写法 | 结果 |
|---|---|
| `[flat]`（一层） | 抛 `float has no len()` |
| `[[flat]]`（两层） | `ok=True` 但**非白 0** |
| `[[[flat]]]`（三层） | `ok=False`，不渲染 |

**两层形状是对的，却裁成空** —— 说明掩码没问题，是**被裁剪的内容画到别处去了**。

看 `_render_clipped` 的实现：

```python
tmp = Canvas(x1 - x0, y1 - y0, (0, 0, 0, 0))
saved = self._offset
self._offset = (-x0, -y0)      # ← 设了偏移
draw_fn(tmp)                    # ← 但 _path 根本不读 self._offset
```

`_offset` 是 `SoftRenderer` 的属性，而真正写像素的是 `Canvas.fill_polygons` ——
它从来不看 `_offset`。所以内容按完整页面坐标画到一块只有裁剪区大小的小画布上，
全落到外面去了，`tmp` 全透明，合成后自然一个像素都没有。

**修**：给 `Canvas` 加 `off` 属性，`fill_polygons` 里先减掉它；
`_render_clipped` 改成 `tmp.off = (x0, y0)`。

修完手工验证（20×4mm 的红条，裁剪区 20×20mm）：

```
裁剪后 ok=True 非白 2832
```

`20mm × 4mm @150dpi = 118 × 24 = 2832` —— **完全吻合**。

再把三层结构接回复合对象（`it["clip"] = [clip_rect]`），实测 `out/cg2_test.ofd`：

```

非白：16993（不裁）→ 13924（裁后）
```

渲染图：红条被裁到 20mm 边界内，绿块 20×20 落在 (30,30)–(50,50) ✓

### 这个 bug 的教训

**形状对、掩码对、结果还是空**的时候，问题在"画到哪去了"，不在"裁成什么样"。
`self._offset` 设在一个类上、读在另一个类里，中间没有约束——这种跨层约定
必须有代码读才算数。

### 顺带记下 clip 的正确形状

```
[ 组[ 子路径[ 扁平坐标 x0,y0,x1,y1,... ] ] ]
```

- 最外层：**组**的列表，**组间取交集**（8.4）
- 每个组内：**子路径**的列表，**组内取并集**
- 每个子路径：**扁平**坐标数组，不是点对

三层少一层就出错：少到一层抛 `float has no len()`，两层能跑但裁空（偏移 bug）。

## 附三十三：C / Rust 替换光栅化内核的实测

### 实验设计

三个实现用**同一份几何、同一个算法**，只比语言：

- 几何：A4 @150dpi（1240×827）的圆，720 段
- 算法：4 条子扫描线 + 非零环绕 + span 累加 + 0~255 归一化
- 代码：`tools/bench/bench_c.c`、`bench_rs.rs`、`bench_all.py`

**先证明算法等价**：三者输出的非零像素数都是 **436374**，逐字节相同。

### 单函数耗时

| 实现 | 平均 | 相对 Python |
|---|---|---|
| Python（`raster.fill_coverage`） | 179.7 ms | 1× |
| C（`gcc -O2`） | 2.456 ms | **73×** |
| Rust（`rustc -O`，`sort_unstable_by`） | 2.406 ms | **75×** |

**C 与 Rust 持平**，差 2% 以内。Rust 最初用 `sort_by` 是 2.577 ms，
换成 `sort_unstable_by` 后反超 C。

### 关键坑：ctypes 的数据复制会吃掉一半以上的收益

| 调用方式 | 耗时 | 加速 |
|---|---|---|
| 纯 Python | 179.7 ms | 1× |
| Python → C，**C 里 malloc 再复制回来** | 17.0 ms | **10.6×** |
| Python → C，**零拷贝写进调用方的 bytearray** | **2.56 ms** | **70×** |

`bytes(ptr[:w*h])` 复制 102 万字节要花 14 ms —— **比计算本身慢 6 倍**。

所以给 Python 用的正确接口是：

```c
void ofd_fill_coverage_into(const double *pts, int npts,
                            int W, int H, int evenodd, int ss,
                            unsigned char *out);   // 调用方给缓冲
```

Python 侧用 `(ctypes.c_ubyte * (w*h)).from_buffer(buf)` 把 `bytearray` 的地址传进去。

### 真实整页的收益远小于单函数

只把 `fill_coverage` 换成 C 版，真实发票整页（210×140mm @150dpi）：

| 版本 | 整页耗时 | 加速 |
|---|---|---|
| 纯 Python | 816.6 ms | 1× |
| 换 fill_coverage | **436.1 ms** | **1.87×** |

**为什么不是 70×**：`fill_coverage` 只占整页的一小部分，剩下的
`fill_polygons`（逐像素混合）、`_text`（字形解析与描边）、`pngcodec.decode`
都还是 Python。

**另外非白像素差了 1988（约 3%）** —— 不是完全等价，接进去之前得逐页比对。

### 结论

| 问题 | 答案 |
|---|---|
| C 和 Rust 哪个快 | **持平**，Rust 用 `sort_unstable_by` 略快 2% |
| 能快多少 | 单函数 **70~75×**；整页只换一层 **1.87×** |
| 最大的坑 | **ctypes 数据复制**，不做零拷贝只有 10× |
| 值得做吗 | 要整页大幅提升，得把 `fill_polygons` 的混合循环、`pngcodec` 一起换，工作量从"两个函数"变成"半个渲染器" |

### 如果真要做，路径是什么

1. 写 `raster_c.c` 提供零拷贝接口（已经有了雏形）
2. `ofdlite/raster.py` 里做**软降级**：能 `ctypes.CDLL` 加载 `.so` 就用 C，加载不到就用纯 Python
3. 同样处理 `fill_polygons` 的混合循环（这是第二大热点）
4. `packaging/build_deb.sh` 加一步编译 `.so`，并处理交叉编译（arm64/amd64 各编一份）
5. 全量回归 + 逐页像素比对（上面那个 3% 差异必须先查清）

**代价**：破坏"纯 Python 无第三方依赖"这条自加约束；多一个构建步骤；
交叉编译要维护两套产物。

**收益**：单函数 70×，但整页取决于换到哪一层。

## 附三十四：Rust 内核落地（第一块：扫描线光栅化）

### 为什么选 Rust 不选 C

速度实测持平（2.456 vs 2.406 ms），但「最稳」这条是决定性的：

- C 的光栅化里越界写一个字节 → 随机崩溃或画错，可能几个月才暴露
- Rust 编译期就过不去

交叉编译和静态链接也是 Rust 更省事（`rustup target add` 一条命令、musl 完全静态）。

### 结构

```
ofdlite/rustcore/
    Cargo.toml          crate-type = ["cdylib"]，panic = "abort"
    src/lib.rs          光栅化 + 像素混合，C ABI
    libofd_core.so      331 KB（strip 后）
ofdlite/_fast.py       软降级加载器
```

**软降级**：`_fast` 按顺序找 `.so`（包内 → 源码树构建产物 → dylib/dll），
找到就用 Rust，找不到回落纯 Python。**测试永远能跑，不依赖编译产物。**

### 接口

```c
// 零拷贝：调用方给缓冲
void ofd_fill_coverage(const double *pts, int npts,
                       int w, int h, int evenodd, int ss, unsigned char *out);
void ofd_fill_coverage_multi(const int *counts, int nsubs, const double *flat, ...);
void ofd_blend(const unsigned char *cov, int w, int h,
               unsigned char *buf, uint8_t r, g, b, a);
const char *ofd_core_version(void);
```

Python 侧用 `(ctypes.c_ubyte * (w*h)).from_buffer(bytearray)` 传地址 ——
**不做零拷贝的话，复制 100 万字节要 14 ms，把 70× 降到 10×**（附三十三测过）。

### 实测

单函数（A4 @150dpi 的 720 段圆）：

| 实现 | 耗时 | 加速 |
|---|---|---|
| 纯 Python | 179.7 ms | 1× |
| **Rust 内核** | **2.875 ms** | **62.5×** |

**结果逐字节一致**：两者非零像素都是 436374。

真实发票整页（210×140mm @150dpi）：

| 版本 | 整页 | 非白像素 |
|---|---|---|
| 纯 Python | 816.6 ms | 62836 |
| **含 Rust 内核** | **516.5 ms** | **62836** |

**1.58× 加速，像素完全一致。**

### 踩的坑：多子路径的环绕语义

第一版把多子路径**逐个算再取最大覆盖率**，结果整页非白多了 2333（3.7%）。

原因：标准 9.2 的非零环绕要求**把所有子路径的边放在一起**计数，
重叠区会相互抵消或叠加。逐个算再取并集，重叠区变成「谁大听谁的」，不是一回事。

改 Rust 支持一次算完（`ofd_fill_coverage_multi` 接受 `counts` 数组），
但分边实现还没对上：两子路径同向嵌套时，纯 Python 得 10000 像素、Rust 得 9424。

**所以多子路径暂时回落纯 Python**，只有单子路径走 Rust。
单子路径占绝大多数，这块已经验证过逐字节一致。

要修多子路径的分边，得单独核 `fill_span_edges` 的索引计算 —— 记为待办。

## 附三十五：JPEG 热点搬 Rust —— 试了，但没敢接

### profile 结果出乎意料

### 写了三个 Rust 函数

```c

                      int w, int h, int cw, int ch, int sh, int sv, uint8_t *out);

void ofd_idct8x8(const int32_t *coef, const uint16_t *qt, uint8_t *out);
```

`_to_rgb` 的做法：把 Cb/Cr 的贡献**预计算成 256 项查表**（系数固定，没必要每像素乘），
循环里只做加法和 clamp。

### 单张图确实快了 5.65 倍

|---|---|

### 修对了两处，现在逐字节一致

**bug 1：Y 平面的行宽不是图像宽度**

```python
yw = ys["bw"] * 8      # 1812 宽对齐到 MCU 后是 1824
```

平面按 8×8 块存、块数按 MCU 对齐，所以 `yw` 可能大于 `w`。
我第一版用 `w` 当行宽，整幅图逐行错位 —— 差 31722 像素就是这么来的。

**bug 2：改 `yrow` 时把 `dst` 的索引也带偏了**

```rust
ys[yrow + x]        // 源：yrow = y * yw（对齐后的行宽）
dst[(yrow+x)*3]     // 目标：这里必须用 y * w + x
```

混用直接写越界：`index out of bounds: the len is 5773032 but the index is 5773032`。

**bug 3：预先取整让结果差 1**

第一版把 `1.402*Cr` 先取整再和 Y 相加，而 Python 是浮点算完一次性取整：

```python
r = Y + 1.402 * Cr      # Python
int(r + 0.5)
```

改完 1、2 之后还差 1267 像素，就是这个。表里存**浮点**贡献才对。

## 附三十六：像素混合搬 Rust —— 又是两个精度坑

### 接的是哪一段

`Canvas.fill_polygons` 算完覆盖率后，有一段逐像素混合：

```python
for row in range(y1 - y0):
    for col in range(mw):
        cvr = mb[base_m + col]
        ...
        buf[i] = int(buf[i] * iv + r * fa)
```

A4 一页几百万次迭代。Rust 侧加了 `ofd_blend_rect`（带 `ox/oy` 偏移，
只处理 bbox 那一小块，不是整幅画布）。

### 坑一：`+0.5` 让结果差 21 个像素

第一版写成四舍五入：

```rust
bufs[o] = (bufs[o] as f32 * ki + r as f32 * k + 0.5) as u8;
```

而 Python 是 `int(...)` —— **截断**，不是四舍五入。

非白像素 63931 vs 63952，差 21。

### 坑二：f32 让结果再差一个色阶

去掉 `+0.5` 后非白一样了（都是 63952），但 **sha256 仍不同**。

原因：Python 的 `iv`、`fa` 都是 f64，我 Rust 侧用了 f32。累积到 `as u8` 时差 1 个色阶。

改成 f64 之后 sha 才一致。

### 结果

WPS 第 2 页：两条路径 sha256 都是 `d3617207956832d2`，**逐字节相同**。

四页合计：

| 路径 | 耗时 |
|---|---|
| 纯 Python | 7.92 s |
| **Rust 全开** | **3.46 s** |

**2.29×**。

### 累计账（从最初版本到现在）

| 阶段 | 四页合计 |
|---|---|
| 最初（纯 Python，无抗锯齿优化） | 14.66 s |
| 抗锯齿 + 矩形快速路径 | 7.92 s |
| **+ Rust 光栅化 + 色彩转换 + 混合** | **3.46 s** |

**整体 4.2×**，且**像素逐字节一致**。

### 现在接了哪些 Rust

| 函数 | 状态 |
|---|---|

### 精度对齐的三条经验

搬编译型实现时，浮点语义必须逐条对齐，否则就是「非白数量一样、sha 不一样」这种难查的差：

1. **取整方式**：`int(x)` 是截断，不是四舍五入
2. **精度**：Python 的 `float` 是 f64，Rust 侧不能用 f32
3. **运算顺序**：`Y + 1.402*Cr` 要浮点算完再取整，不能先把 `1.402*Cr` 取整

### 一、查出并修掉的真 bug（5 处）

#### 1. 第 13 章复合对象：矢量图像资源元素名少一个 `ic`

- 标准：表18（`CompositeGraphicUnits` / `CompositeGraphicUnit`）+ 附录 A `Res.xsd:81` 都是
  `CompositeGraphicUnit`。
- 实现：`ofdlite/model.py` 查的是 `CompositeGraphUnit`（少 `ic`）。
- 后果：**标准件里 `ResourceID → CT_VectorG → Content` 一个都取不到**，复合对象渲染成空白。
- 为什么以前没发现：`tools/mk_cg2.py` 的样本也按错拼写写（第 46~50 行）——自造样本跟着实现走，
  把 bug 测成了通过（附三十一当时"复合对象修好了"，只对非标准写法成立）。
- 取证：`out/probe_cg_name.py`，同一份文件两种拼写对比 —— `CompositeGraphUnit` 命中、`CompositeGraphicUnit` 返回 `None`。
- 修法：两种拼写都认（兼容已存在的野文件）。
- 验：`out/probe/probe_composite.ofd`（XSD 4/4 通过）→ 展开子对象 1 个，填充 `(0, 0.784, 0)` = 标准绿色。

#### 2. 表27 的逐通道十六进制颜色全部丢失

- 标准：表27 的示例写法就是 `"#11 #22 #33"`（RGB）、`"#FF"`（GRAY）、`"#11 #22 #33 #44"`（CMYK）。
- 实现：旧 `parse_color` 只认整串 `"#RRGGBB"`，遇到逐通道写法返回 `None`（退化成透明/默认色）。
- 后果：用这种写法生成的文件，颜色整片丢失。
- 修法：先按空白切 token，全部以 `#` 开头就逐通道解；单 token 支持 1/2/3/6/8 位（`ofdlite/colors.py`）。
- 验（`probe_color.ofd`，五个色块中心逐像素）：

```
逐通道hex  "#11 #22 #33" -> (17, 33, 51)
GRAY       "#FF"          -> (255, 255, 255)
BPC=4      "15 0 0"       -> (255, 0, 0)
调色板      Index=1        -> (0, 0, 255)
CMYK 资源   "0 255 255 0"  -> (255, 0, 0)
```

#### 3. 表25 / 表27 的 `BitsPerComponent` 没参与换算

- 标准：通道取值范围是 `[0, 2^BPC-1]`，BPC 有效值 1/2/4/8/16，默认 8。
- 实现：一律 `/255`。BPC=4 时 `15` 是满值，被算成 6% 的暗色。
- 修法：`channel_scale(bpc) = 2^BPC-1`；通道越界按表27 明文"超出区间按默认颜色处理"。
- 验：BPC=4 `"15 0 0"` → 纯红；BPC=16 `"65535 0 0"` → 纯红。

#### 4. 8.3.1 / 表25 / 表26：`ColorSpace` 是资源 ID，却拿数字猜空间；`Index` 调色板没实现

- 标准：表26 的 `ColorSpace` 是 `ST_RefID`，要回资源查 `Type`（GRAY/RGB/CMYK）；
  `Value` 不出现时按 `Index` 从 `Palette/CV` 取色。
- 实现：旧代码用一张 `_STD_SPACES` 表把 `"1"`→rgb、`"5"`→rgb 猜，资源里的 `Type/BPC/Palette` 完全没用；
  `Index` 也没读。CMYK 文件会被当 RGB 画成怪色。
- 修法：`Document.find_colorspace()` 返回 `{type, bpc, palette}`；颜色统一走新的 `parse_color_el()`。
- 验：资源里 `CS5 = CMYK` 的 `"0 255 255 0"` → 纯红；`Index=1` → `(0,0,255)`。

#### 5. 表21：绘制参数 `Relative` 继承没做，`DrawParam` 里的 `DashOffset` 丢了

- 标准：绘制参数可以继承"基础绘制参数"并形成嵌套，子参数覆盖同名属性；表21 明列 `DashOffset`。
- 实现：`parse_draw_param` 只读 7 个属性（无 `Relative`/`DashOffset`），`find_drawparam` 不做合并。
- 后果：靠 `Relative` 组织样式的文件，描边颜色/线宽整段丢失（回落到默认黑 0.353mm）。
- 修法：`find_drawparam` 沿 `Relative` 递归合并（深度上限 16 防环）；`parse_draw_param` 收全 9 个属性。
- 验：`probe_drawparam.ofd` —— `DP20 Relative="10"` 只写 `Join="Round"`，
  实际拿到 `红 + 1.000mm + round`（`DP10` 的 `LineWidth=1.0` 与红色描边都继承到了）。

## 附三十九：第 3 页的差异查清了 —— alpha 语义写错

（附三十八记的「未查清」到此结案。）

### 定位

写了个诊断脚本 	ools/diag_page3.py，把 Rust 的四个入口逐个关掉，
看哪个关掉之后 sha 与纯 Python 一致：

`
全开                 6dd43d8b
禁 blend_rect        13045dd3   ← 与纯 Python 相同
禁 fill_coverage     6dd43d8b
禁 ycbcr_to_rgb      6dd43d8b
禁 idct8x8           6dd43d8b
纯 Python 基线       13045dd3
`

**是 ofd_blend_rect。**

### 根因：alpha 的合成规则我按常识写了，没跟 Python 对齐

Python 的 ill_polygons 里：

`python
na = int(sa * cvr / 255)
if buf[i + 3] < na:
    buf[i + 3] = na
`

**「取较大值」**，不是 source-over。

我写成了：

`
ust
bufs[o + 3] = (bufs[o + 3] as f64 * inv + 255.0 * fa) as u8;
`

这是标准的 source-over，语义上更「正确」，**但与 Python 不一致**。

这一层的目标不是「更正确」，是**与纯 Python 路径逐字节一致**——
两条路径必须能互换，否则 OFD_NO_RUST=1 这个降级开关就失去意义。

### 还漏了一个分支

`python
fa = (cvr / 255.0) * a
if fa >= 1.0:
    buf[i] = r; ...       # 覆盖率达到不透明，直接写
`

Rust 侧原来没有这个短路，已补。

### 修完

五个组合全是 13045dd3，**四页 sha 全部一致**：

`
da5740fd  d3617207  13045dd3  30eb721d
`

| 路径 | 四页耗时 |
|---|---|
| 纯 Python | 12.16 s |
| **Rust 全开** | **5.07 s** |

**2.40×**。

### 教训

搬实现时，「这段逻辑怎么写」**只能有一个答案：跟被替代的那份一样**。

哪怕原实现看起来不够「标准」（这里是取较大而不是 source-over），
只要它是当前的产出基准，就必须逐字节对齐。
**否则降级开关变成换个算法，而不是换个执行引擎。**

## 附四十：nonzero span 的划法 —— 找准了一处，但没修完

### 这轮 profile 的发现（很重要）

第 1 页 1.476 秒里，**
aster.fill_coverage（纯 Python）被调 429 次、占 0.428 秒（29%）**，
而 _fast.fill_coverage（Rust）被调 547 次。

**429 次走纯 Python 的原因就是多子路径回落。** 所以修好多子路径的收益
（29%）比搬 _text 更直接。

### 找到的语义差异

Python 的 nonzero：

`python
wind = 0
start = None
for x, d in xs:
    prev = wind
    wind += d
    if prev == 0 and wind != 0:        # 从 0 变非 0：开
        start = x
    elif prev != 0 and wind == 0:      # 从非 0 变 0：闭
        spans.append((start, x))
`

**「跨越零点」才开闭 span**。

我原来写的是：

`
ust
wind += cr[i].dir;
let inside = wind != 0;     // 当前非 0 就画
if !inside { continue; }
`

**这在 wind 从 2 变 1（都非 0）时还会继续画** —— 而正确做法是那一整段本来就连着。

已按 Python 的「跨越零点」重写，同时把 span 先收集再统一处理
（顺带把 even-odd 也整理成同一形状）。

### 但真实页面还是不一致

修完单子路径的四页 sha 仍全部一致（da5740fd d3617207 13045dd3 30eb721d），
回归也过；**多子路径仍有 23 个像素偏差**（15×14 的小区域，4 个子路径）。

	ools/diag_multi.py 能把第一个不一致的多边形 dump 成 out/multi_probe.py，
下次可以直接拿它做单点复现。

**多一点线索**：diag_multi.py 里直接调 lib.ofd_fill_coverage_multi 时，
_fast._try_load() 返回的是**缓存过的旧 lib**，所以那次诊断测的可能仍是旧二进制。
下次要先 _fast._lib = None 再调。

### 状态

多子路径**继续回落纯 Python**（安全），单子路径与混合、JPEG 三项已逐字节一致。

## 附四十一：多子路径的偏差形态已定位到「左侧多画」

用 	ools/diag_multi_one.py 把那个 15x14 的用例打成覆盖率矩阵（.=0 :=小 +=中 #=满）：

`
纯 Python                     Rust
 0123456789012345             0123456789012345
  ..:+.:.........              ..++::.........
  ..........::...              ..+:::....::...
  .+++:+++++++...              .++:++++++++...
`

**Rust 在左侧 x=2..5 多出一片**，形状对但范围宽。

这说明 span 的左端点（start）取值不同，或者闭合时机不同。

### 已经排除的

- span 的开闭规则（已按 Python 的「跨越零点」重写，单子路径四页 sha 仍全一致）
- _fast._lib 缓存（诊断脚本已清，测的是新二进制）

### 待查方向

1. cr 的排序：Python 用 xs.sort(key=lambda t: t[0])（稳定排序），
   Rust 用 sort_unstable_by —— **交点 x 相等时顺序不同**，
   会让 prev == 0 / wind == 0 的判定错位。**这是最可能的原因**。
2. spans 收集完后是否漏了 x1 <= x0 的过滤顺序
3. int(x0) 与 loor 在负值上的差异（本例都是正值，排除）

**下一步**：把 sort_unstable_by 换成 sort_by 试一次，若仍不同再查 cr 的内容。

### 状态

多子路径继续回落纯 Python（安全）。单子路径、混合、JPEG 三项逐字节一致。
四页 6.05s vs 14.54s（2.40x）。


## 附四十二：多子路径的归零 —— 决定放弃让它走 Rust

### 二分结果

用 out/multi_probe.py 那个 4 子路径的用例（点 14/131/50/115）：

| 组合 | 差异像素 |
|---|---|
| 单个子路径 0 | 0 |
| 单个子路径 1 | 0 |
| 单个子路径 2 | 0 |
| 单个子路径 3 | 0 |
| 任意两两组合 | 0 |
| **四个一起** | **23** |

**单个和两两全对，四个一起就错。** 问题出在多个子路径的交点在同一条
扫描线上交错时的环绕计数。

### 已排除的四条

| 试过的 | 结果 |
|---|---|
| 排序稳定性（sort_unstable_by → sort_by） | 仍是 23，无变化 |
| 水平边过滤（y0 == y1 → bs(y1-y0) < 1e-12，对齐 Python） | 仍是 23，无变化 |
| .so 缓存（_fast._lib = None 后重载） | 已确认测的是新二进制 |
| span 开闭规则（改成 Python 的「跨越零点」） | 单子路径四页 sha 仍一致，多子路径仍差 23 |

两处改动（稳定排序、近似水平边）都让 Rust 更接近 Python，**保留**——
它们本身是对的，只是没根治。

### 决定：放弃

理由：

1. **第 4 次尝试**，每次都是「更接近但不等价」
2. 剩下的差异在复杂环绕交互上，要逐条比对 cr 的内容才可能定位，
   而这一步没有可复用的调试手段（Python 侧也没有中间量导出）
3. **多子路径已经回落纯 Python，正确性无风险**
4. 收益是光栅化那 29%，但继续纠缠的代价已超过收益

**保守回落优于一个「看起来对」的实现**——这条原则在附三十五（JPEG 像素差 31722）
和附三十八（alpha 语义）都验证过。

### 保留下来的两处改动

`
ust
// 稳定排序：交点 x 相等时顺序影响 prev/wind 的判定
cr.sort_by(|a, b| a.x.partial_cmp(&b.x).unwrap_or(Ordering::Equal));

// 近似水平边也跳过（Python 侧是 abs(y1-y0) < 1e-12）
if (y0 - y1).abs() < 1e-12 { continue; }
`

单子路径四页 sha 仍全部一致，回归全绿。

| **Rust 全开** | **6.05 s** |

**2.40×**。
