## 三、生成

入口：`tools/make_ofd.py`（JSON 规格）+ `tools/make_sample_ofd.py`（写死样本）。
产物一律过 XSD：当前样本 **5/5 条目通过**。

### 已实现 ✓

| 对象 / 机制 | 支持范围 |
|---|---|
| 页面 | 尺寸可配、多页、每页独立 PhysicalBox |
| 文字 | 内容、字体、字号、粗体、斜体、颜色、HScale、CharDirection、ReadDirection |
| 图形 | PathObject 全套运算符原样传入；矩形（含圆角 A 弧）、椭圆、直线 |
| 描边 | 线宽、颜色、虚线 DashPattern |
| 填充 | 颜色（或留空不填充） |
| 图像 | PNG，自动放入 `Doc_0/Res/` 并登记 MultiMedia |
| 资源 | PublicRes（ColorSpace + Fonts）、DocumentRes（MultiMedias） |
| 结构 | OFD.xml / Document.xml / 页树 / 三层资源引用 |

### 未实现 ✗

| 缺口 | 说明 |
|---|---|
| 渐变与底纹 | 只能纯色填充 |
| 裁剪区 | 生成不了 Clips |
| 复合对象 | 不能把多个对象打包成 CompositeObject |
| 模板页 | 不能生成 TemplatePage（只能读现有的） |
| 注释 / 签章 | 不能生成 |
| 动作 | 不能生成跳转、链接 |
| 大纲 | 不能生成书签 |
| 视频 | — |

**量化**：标准里的图元对象共 5 类（图形、图像、文字、视频、复合），
生成器覆盖 4 类（缺视频），且这 4 类只支持「纯色填充」这一档着色方式
（缺渐变与底纹两档）。

## 四、修改

入口：`ofd_cli.py edit`（命令行）、桌面端属性面板、网页端属性面板。
编辑模型的骨架在 `ofdlite/edits.py`。

### 已实现 ✓

| 能力 | 实测 |
|---|---|
| 改文字内容 | `--replace 旧=新`，实测命中 1 处 |
| 改字号 / 颜色 / 字体 | 属性面板与 API |
| 页管理 | 插入、删除、排序 |
| 撤销 / 重做 | 快照机制，模板页对象也可撤销 |
| **增量保存** | 只重写被改的 ZIP 条目，其余按原字节回填 |
| 保存后校验 | 改完仍 XSD 全通过（实测 5/5） |
| 签名失效提示 | 三端都提示「仅用于版式调整，不得用于报销入账归档」 |

### 未实现 ✗

| 缺口 | 影响 |
|---|---|
| **改几何** | 不能移动 / 缩放 / 旋转已有对象；只能用 JSON 重新生成 |
| **增删对象** | 不能在某页插入一个新文字或新框线（除桌面端的插入图片/方框） |
| 改路径 | 不能编辑 AbbreviatedData |
| 改资源 | 不能替换图片、换字体文件 |
| 改注释 | 不能编辑或添加注释 |
| 改模板页结构 | 能改模板里的对象属性，不能改模板的引用关系 |
| 合并 / 拆分文档 | 不能把多个 OFD 合成一个，或抽取某页成新文件 |

**这是三项能力里最弱的一环**。当前定位是「改文字层面的版式调整」，
不是「所见即所得的排版工具」。要做后者，缺的是对象选择 + 变换矩阵编辑
+ 对象树增删这一层，工作量约等于重写一个编辑模型。

## 六、一句话结论

- **查看**：能读能画真实电子发票，四类图元与坐标体系完整，
  **缺 5 项着色与裁剪机制**，遇到会跳过并告警而不崩。
- **生成**：能从零造出合规文档并通过 XSD，
  但着色只有纯色一档，**没有渐变、底纹、裁剪**。
- **修改**：只到「改文字属性 + 页管理」，**不能改几何、不能增删对象**，
  这是与「排版工具」之间最远的一段。

三项里查看最成熟，生成够用，修改最弱。

**关于那几个百分比**：78% / 60% / 45% 是按标准章节的**条目数**估的，不是按代码行数，
也不是严格加权。它的用处是排序（哪块最弱、先补什么），不是精确度量。
真正可靠的是上面那三张「已实现 / 未实现」清单——每一条都能在代码与实测里对上，
清单里的缺口才是事实。

## 七、已发现并修掉的实现瑕疵

写这份评估时对着标准复核代码，发现一处不属于标准的写法，已删除：

| 位置 | 问题 | 处置 |
|---|---|---|
| `model.py` 的 `has_stroke()` | 判断过一个 `StrokePattern` 元素——**标准里不存在**（`Page.xsd` 出现 0 次），是凭印象写的 | 已删除，改为按标准真实存在的三处依据判断：`StrokeColor` 子元素、`LineWidth` 属性、`DrawParam` 引用 |

后果原本无害（只在 `Stroke` 属性缺失时作为启发式），但会误导后续维护，
也说明「凭记忆写标准」确实会出错——这类问题只能靠对着 schema 和正文逐项核。

## 附：复跑方法

```bash
# 查看
python3 tools/ofd_cli.py info  文件.ofd
python3 tools/ofd_cli.py render 文件.ofd -o out/p1.png --dpi 200

# 生成（含 XSD 校验）
python3 tools/make_ofd.py tools/sample_invoice_spec.json -o out/x.ofd --validate

# 修改
python3 tools/ofd_cli.py edit 文件.ofd --replace 旧=新 -o out/new.ofd
python3 tools/validate.py out/new.ofd

# 标准结构校验
python3 tools/validate.py 文件.ofd --verbose
```

真实发票实测数据（本机，2026-10-29 复测）：

```
包内条目 10 · 页 1 · 210.0x140.0 mm
对象 72 · 路径 17 · 文本 53 · 图片 2 · 字体 7 种
渲染告警：无
结构校验：7 个条目中 3 通过 / 4 不符合（均在该文件自身，非本工具产出）
```

那 4 处不符合是文件本身的问题（`ImageObject` 缺 `ID`、`CustomTags` 用 `TypeID`
且缺 `NameSpace`、模板里颜色子元素写在 `AbbreviatedData` 之前），
本工具只读不改，读的时候按宽容模式处理。详见 `标准核对记录.md`。
