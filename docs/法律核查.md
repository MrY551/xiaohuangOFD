## 二、著作权

### 2.1 权属

依据《著作权法》第二条、第十一条，《计算机软件保护条例》第五条：
软件著作权自软件开发完成之日起产生，**不以登记为取得要件**。你独立开发，著作权归你。

已有署名证据（本项目内）：

```

tools/ofd_cli.py --version 输出作者行
app/mainwindow.py          关于框
web/static/index.html      页脚
deb Maintainer / copyright
```

`tools/check_authorship.py` 可随时核验这五处是否被删改。

### 2.2 原创性

与同语言实现 easyofd（PyPI sdist，3486 有效行）做行级 + 标识符级比对：

```
本项目有效代码行 7978
完全相同的行 53 条（0.66%），构成：import 7 / def·class·装饰器 2 / except 1 / return 1 / 其他 7
函数名重合 10 个：Document / Page / PathObject / TextObject / TextCode /
                  ImageObject / CompositeObject / Layer / TemplatePage / __init__
```

前九个名字来自 GB/T 33190 的元素定义（标准原文分别出现 4/14/14/3/4/2/2/2/2 次），
按标准实现必然同名；纯实现层命名（`to_pdf` / `add_image` / `hit_test` / `subpaths`）
在对方代码里 0 命中。第三方版权痕迹 0 处。

与前端实现 ofd.js（JavaScript，Apache-2.0）的同语言比对：

```
本项目有效代码行 8802（含 JS）   对照 1111（ofd_render.js / ofd_util.js /
                                          HelloWorld.vue / ofd.js / pipeline.js）
完全相同的行 4 条（0.05%）：'use strict'; / } catch (e) { /
                            div.appendChild(img); / return null;
函数名重合 0 个
```

**结论：两个方向都不构成《计算机软件保护条例》第二十四条所指的抄袭，可主张独立开发。**

### 2.3 建议办理软著登记

登记不是取得权利的前提，但有三项实际作用：诉讼时作为初步证据、投标与高企认定要、可作价出资/质押。

- 受理机构：中国版权保护中心（`register.ccopyright.com.cn`，软件著作权咨询 010-61090099）
- 材料：
  1. 申请表（在线填，软件名称写"小黄OFD 版式文档处理软件"，版本 V1.0）
  2. 源程序：前 30 页 + 后 30 页，每页 50 行，共 60 页（不足 60 页全交）。本项目 37 个 `.py`、9851 非空行，够 60 页
  3. 文档：用户手册或设计说明书（README 扩写即可，20–30 页）
  4. 身份证明（自然人身份证 / 企业营业执照）
- 周期：一般 30–60 个工作日，可加急（收费）

**登记前把版本号定死（V1.0.0），后续大改再办变更或新版本登记。**

## 三、自身许可的法律效力

`LICENSE` 现在是自定义许可，不是 MIT。有效性分析：

| 条款 | 法律依据 | 效力 |
|---|---|---|
| 允许安装、使用、复制、修改、分发（含商业） | 《著作权法》第十条（复制权、发行权、信息网络传播权、改编权）许可 | 有效 |
| 分发必须保留署名与联系方式 | 《著作权法》第二十二条但书的反面 —— 许可附条件 | 有效，属"附条件的授权" |
| 修改版须标注「非官方修改版」 | 同上，防止混淆来源 | 有效 |
| 禁止删署名后以他人名义发布 | 《著作权法》第五十三条（不得删除或改变权利管理信息）；《反不正当竞争法》第六条 | 有效，双重保护 |
| 按「现状」提供、不担保 | 《民法典》第五百零六条（免责条款） | 有效，但**故意或重大过失不免责** |

需要注意的两点：

1. **不是"开源许可"**。OSI 认可的开源定义不允许限制署名保留以外的额外条件（如强制标注修改版可能被认为有歧视性）。所以对外不要说"开源"，说"源码公开 / 可自由使用"。README 里已经统一表述为"项目许可"。
2. **分发必须附许可全文**，否则被许可人可主张未收到条件。deb 里已带 `LICENSE` 与 `copyright`。

## 五、标准与专利（本节最需要注意）

### 5.1 标准原文自认可能涉及专利

GB/T 33190-2016 前言原文：

> 本标准按照 GB/T 1.1—2009 给出的规则起草。
> **请注意本文件的某些内容可能涉及专利。本文件的发布机构不承担识别这些专利的责任。**

起草单位：中国电子技术标准化研究院、**福建福昕软件开发股份有限公司**、**北京数科网维技术有限责任公司**、
**北京方正阿帕比技术有限公司**、**北京书生电子技术有限公司**。

即：标准里可能含上述公司的专利，发布机构不负责排查。

### 5.2 实际风险评估

| 维度 | 事实 | 影响 |
|---|---|---|
| 是否有公开专利池 | 无 | 无统一收费主体 |
| 是否有 FRAND 声明 | 未见 | 无许可承诺，也无拒绝许可的公开表示 |
| 是否有诉讼先例 | 公开渠道未见 OFD 格式实施者被诉 | 无判例参考 |
| 标准性质 | GB/T，推荐性 | 非强制实施，但实施是行业通行做法 |
| 你实施的范围 | 读写文件格式（互操作） | 属标准正常实施，非制造专利产品 |

**判断：实际风险极低，但不能说"零"。**

### 5.3 已排查到的同类专利

| 专利 | 申请人 | 内容 | 与本项目的关系 |
|---|---|---|---|
| CN120012166A | 福昕鲲鹏（北京）信息科技 | 开放版式文档 OFD 中页面对象的权限控制方法及装置（语义树 + 节点权限 + 备份文档） | 覆盖「权限控制的实现方式」，本项目不实现该机制，不落入其权利要求 |

福昕鲲鹏公开专利信息 66 条，均为**具体实现优化**（权限控制、对象管理一类），
未见覆盖「按标准解析 + 渲染版式文档」本身的权利要求。这正是国标实施类软件
一般不构成专利侵权的结构性原因：标准规定的是**数据格式与语义**，
专利保护的是**实现某功能的具体技术方案**，两者不在同一层面。

公开渠道未检索到任何因实施 GB/T 33190 而被主张专利的案例。

### 5.4 本项目自身的专利点

已梳理 8 个技术点并作出权利保留声明，清单见 [`专利点声明.md`](专利点声明.md)。
**这些技术点尚未提交专利申请**，声明的作用是保留权利、划定主张范围，不是「已申请」。
需要特别注意的一层关系：

- 本项目代码已于 2026-10-29 在公开仓库发布，依据《专利法》第二十二条，
  申请日前的公开构成现有技术；第二十四条的四类例外不覆盖公开代码仓库，
  中国亦无一般性的申请前公开宽限期。
- 因此 `专利点声明.md` 只公开到「技术问题 — 技术手段要点 — 技术效果」，
  不含参数取值与流程分支，完整交底材料不随仓库发布。
- 处置：尽快提交申请；未公开的后续改进（`Clips`、`CT_VectorG`、签章验证）
  先申请再公开；已公开部分以著作权 + 商业秘密为主要保护手段。

### 5.5 若要商业化，建议做一次完整专利检索

在国家知识产权局检索系统（`pss-system.cponline.cnipa.gov.cn`）用

## 七、数据与内容合规

### 7.1 个人信息

《个人信息保护法》第十三条：本地处理、不上传、不共享，属于"为订立履行合同所必需"或"已公开"等情形之外的自处理，
本项目不构成"个人信息处理者"对外提供数据。

技术事实（已在 README 与 THIRD-PARTY 声明）：网页端只监听 `127.0.0.1`，不上传文档内容，
不联网取字体、不联网校验。

**若将来做云端转换服务**，则成为个人信息处理者，需：告知同意、最小必要、加密传输、留存期限、
以及《数据安全法》第二十一条的数据分类分级义务。

### 7.2 电子发票的编辑能力（重点）

技术事实：

- 本软件能修改 OFD 内文字并另存
- 保存只重写改动过的 ZIP 条目，**原数字签名因此失效**
- 软件不验签、不验证签章有效性

法律风险面：

| 条文 | 内容 | 与本软件的关系 |
|---|---|---|
| 《发票管理办法》第二十一条 | 不符合规定的发票不得作为财务报销凭证 | 改过内容的发票即"不符合规定" |
| 《刑法》第二百零六条 | 伪造、出售伪造的增值税专用发票罪 | 若被用于伪造发票，属使用者行为 |
| 《刑法》第二百零九条 | 非法制造、出售非法制造的发票罪 | 同上 |
| 《刑法》第二百八十七条之二 | 帮助信息网络犯罪活动罪 | 明知他人用于犯罪仍提供工具的，可能构成 |

**降低风险的三件事，已经做了两件：**

1. ✅ README / LICENSE / THIRD-PARTY 三处写明"不校验数字签名、不验证签章有效性，不能作为票据真伪的依据"
2. ✅ 保存策略只重写改动条目，不掩盖改动痕迹（签名必然失效，改动可被发现）
3. ⬜ **待补**：在界面与 CLI 的保存路径上给一次明确提示 —— "修改后的文件已破坏原签名，仅可用于版式调整/二次排版，不得用于报销、入账、归档"

第 3 条是**最有效的一条**：它把"工具中立"从口头声明变成用户可见的操作确认，
在个案中能作为"已尽提示义务"的证据。

### 7.3 标准符合性声明

可以说：**"依据 GB/T 33190-2016 实现"**——有 `docs/标准核对记录.md` 逐条对照、
`docs/xsd/` 14 个 XSD、`tools/validate.py` 可复跑（自产样本 6/6 通过）。

不可以说：**"通过国标认证"**——GB/T 是推荐性标准，没有官方认证机构，
市面上所谓"OFD 认证"多为厂商自测或联盟测试，措辞上应避免。
